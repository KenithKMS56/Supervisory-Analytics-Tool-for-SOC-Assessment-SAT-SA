# SAT-SA Architecture & Design Decisions

This document records architectural decisions, context, rationale, and alternatives considered during the development of SAT-SA.

## ADR-001: Strict Adherence to No AI/ML Hard Constraint
- **Decision:** All analytics, detection, scoring, and text rationales are strictly deterministic, relying on DuckDB SQL rule predicates with configurable thresholds, peer-cohort baselines, and static string templates. NS03 and EG11 use a robust z-score (median/MAD) against the peer cohort; the rest of the robust-statistics library in `satsa/peers/` (IQR, CUSUM, EWMA) is implemented but not used by any rule or score.
- **Reason:** We chose full determinism over ML-based detection because the problem statement weights Explainability & Auditability equally with detection performance, and a rule-based system gives supervisors a traceable, court-defensible rationale for every finding: each score can be reproduced by hand from the same inputs, and every finding cites the exact records and thresholds that produced it. This is a design choice made in service of that criterion, not a literal textual mandate in the problem statement for "complete determinism."
- **Alternatives Considered:** Lightweight regression/decision trees, local embeddings. Rejected because they would trade away byte-identical reproducibility and per-finding explainability for a detection-accuracy gain that is unverifiable against the tool's own synthetic validation set (see docs/validation.md's "detector-implementation correctness" framing) and would be far harder for a non-technical examiner to independently audit.

## ADR-002: Dual-Store Architecture (DuckDB + SQLite)
- **Decision:** Store every canonical table as Parquet, one file per table and entity (`data/parquet/{table}/entity_id={entity_id}/data.parquet`, no time partitioning), and analyse it with DuckDB: an assessment loads all tables into an in-memory DuckDB database pinned to one thread (`PRAGMA threads=1`, for reproducible floating-point aggregation). Use SQLite (`data/satsa.db`) for operational state: run manifests, finding cards, review queues, examiner feedback, and hash-chained audit logs.
- **Reason:** DuckDB gives columnar group-by aggregation in SQL without an external server, and Parquet keeps the submitted data compact on disk (sizes measured in `docs/benchmarks.md`). SQLite provides ACID transactional integrity, simple schema migrations, and reliable single-file persistence for audit logs.
- **Correction (quality pass, October 2026):** this ADR used to give the layout as `data/parquet/{entity_id}/{year_month}/...` and to say DuckDB avoids loading entire datasets into RAM. Neither matches the code: the layout is per table and entity, and the tables are loaded into memory for each assessment (assessment peak memory is measured in `docs/benchmarks.md`).
- **Alternatives Considered:** Pure SQLite (insufficient performance for 5M+ rows), PostgreSQL (requires external daemon, violating simple offline air-gap deployment).

## ADR-003: Pure-Python and Local Vendored Assets for Offline Guarantee
- **Decision:** Vendor Apache ECharts locally in `src/satsa/ui/static/echarts.min.js`. All HTML templates render without external fonts or CDN stylesheets. PDF generation uses `reportlab` (pure Python). (Correction during the hardening pass: three templates did load Google Fonts, contrary to this ADR; those links were removed and `tests/test_offline_hardening.py` now statically scans every template/static file and sweeps every GET route under a socket guard, so the claim is enforced rather than asserted.)
- **Reason:** Hard constraint requires SAT-SA to function in an air-gapped environment with no internet access.
- **Alternatives Considered:** CDN references with local cache fallback. Rejected because external network lookups would violate the strict air-gap test.

## ADR-004: Cryptographic Audit Chaining (`prev_hash`)
- **Decision:** Every entry in `audit_log` (and `admin_audit_log`) stores `prev_hash` (the previous entry's hash) and `curr_hash`, a hash over the entry's own fields plus `prev_hash`. Verification walks the chain and recomputes every hash.
- **Guarantee (stated precisely):** for an attacker who can modify stored rows but does **not** recompute hashes, verification detects an edited field, an edited or swapped hash, a relabeled hash algorithm, a deleted, inserted or reordered entry **anywhere except the end of the chain**, and reports the first affected row. It does **not** detect removal of the newest entries, nor a full recomputation of the chain; see ADR-005 for those limits and the external-checkpoint mitigation. (An earlier version of this ADR claimed the chain "detects any unauthorized update, deletion, or tampering"; that overstated it.)
- **Reason:** Tamper-evidence for supervisory audits and inspections without networking or an external ledger.
- **Alternatives Considered:** Blockchain/external ledger (over-engineered and requires networking), signed individual files (difficult to verify sequential insertion).

## ADR-005: SHA3-256 Hash Chain with External Checkpoints, not Post-Quantum Signatures
- **Decision:** New audit entries are hashed with SHA3-256 over `"sha3_256:" + payload` and tagged `hash_alg = 'sha3_256'`; entries written before this change keep `hash_alg = 'sha256'` (plain SHA-256), set by an in-place `ALTER TABLE` default. Verification recomputes each entry with **its own** recorded algorithm, so a chain mixing legacy and current entries verifies end to end. Because the algorithm tag is inside the hashed input, relabeling an entry's `hash_alg` is detected rather than silently switching algorithms. `satsa audit head` prints the entry count and head hash for an examiner to record **off-box**; `satsa audit verify --checkpoint-count N --checkpoint-head H` later confirms the chain still contains that head.
- **Why hash-chaining rather than post-quantum signatures:** the realistic threat to this audit trail is an insider altering records *now* -- e.g. hiding a tuning change or a disposition -- not cryptanalysis of an archived log decades from now. A keyless hash chain addresses that without introducing a signing key that would itself need custody, rotation and protection on an air-gapped host (a signing key stored on the same box an insider controls adds little). For integrity, SHA3-256 already has a comfortable post-quantum margin: Grover's algorithm at best halves the effective security of a preimage search (~128-bit post-quantum for a 256-bit hash); it does not break the function. Post-quantum signatures (e.g. ML-DSA) would matter if entries had to be verifiable by third parties without trusting the host, which is out of scope for this deployment.
- **What this does NOT defend against (stated plainly):**
  1. **Full recomputation.** Anyone with write access to the SQLite file can edit history and recompute every `prev_hash`/`curr_hash` from the genesis value; the rewritten chain verifies. The chain is keyless, so nothing on the box distinguishes it from the original.
  2. **Tail truncation without an external anchor.** Deleting the newest *k* entries leaves a shorter chain that is still internally consistent and verifies.
  Both are only detectable by comparing against a checkpoint recorded somewhere the database's operators cannot edit (paper, a separate system): `satsa audit head` produces it and `satsa audit verify --checkpoint-*` checks it. `tests/test_audit_tamper.py` includes tests that deliberately confirm both limits and confirm the checkpoint catches them. Signed checkpoints, which a verifier can check without trusting the host, are added by ADR-008.
- **Alternatives Considered:** HMAC-keyed chain (needs a secret that an insider on the same host can read); per-entry post-quantum signatures (key custody problem as above, larger entries, new dependency); external transparency log / timestamping authority (requires networking, violating the air-gap constraint).

## ADR-006: The Admin Activity Feed (`live_events`) Is Not Hash-Chained
- **Context:** The NCIIPC Admin Portal shows an *admin activity feed* (operator session monitor) of what SAT-SA's own operators are doing: sign-ins, report downloads, assessment runs, account blocks, role changes. It is backed by the `live_events` table (`record_live_event` / `get_live_events`). These are events about SAT-SA's internal users, not security data collected from CSEs.
- **Decision:** `live_events` stays a plain, non-authoritative table and is **not** hash-chained. The system of record for security-relevant actions is the hash-chained `audit_log` / `admin_audit_log` (ADR-004/005), and every security-relevant event the feed shows has a counterpart written there by the same request: `USER_LOGIN` <-> `login`, `USER_LOGOUT` <-> `logout`, `ACCOUNT_BLOCKED` <-> `USER_BLOCKED`, `ROLE_CHANGED` <-> `ROLE_CHANGED`, `CSE_CHANGED` <-> `CSE_CHANGED`, `ASSESSMENT_*` <-> `ingest`/`run`. `tests/test_activity_feed_hardening.py` enforces this pairing.
- **Consequences:** Someone with database write access can alter or delete feed rows without detection; an examiner who needs evidence must use the audit chains, not the feed. Read-only views (`FINDING_VIEWED`, `REPORT_GENERATED`/`REPORT_DOWNLOADED`) appear only in the feed, consistent with the documented gap that read access is not audited (docs/functional_design.md Section 2). Feed queries are bounded: `since_id` must be a non-negative integer and `limit` is capped at 200.
- **Alternatives Considered:** Chaining `live_events` as a third chain (doubles write cost on hot, high-volume view events and duplicates what the audit chains already prove); dropping the feed (loses the operator-oversight view the Admin Portal needs).

## ADR-007: Exploratory Anomaly Leads Are Not Scored
- **Context:** The 20 rules test conditions someone anticipated. The problem statement also asks the tool to help find "previously unknown indicators" and to "identify anomalies, outliers and suspicious operational patterns", and before this change only 4 of 20 rules compared an entity with its peers (requirement table rows F7, F8).
- **Decision:** `satsa.peers.anomaly_scan` computes a fixed catalogue of about 40 operational rates per entity (the catalogue is code, `METRICS`, so every metric is reviewable) and flags (a) **peer outliers**, robust z (median / 1.4826·MAD with a per-metric spread floor) of at least 3.5 against the entity's peer cohort, and (b) **time shifts**, a two-sided CUSUM over the entity's monthly values tested against its own first three months. The output is a separate kind of record, the *lead*: it is stored per run (`anomaly_signals`, with every computed value in `metric_values`), shown on the entity profile and counted on the portfolio, but it has **no severity, no score, and does not enter the risk index or the review queue**.
- **Reason:** A rule enters the score only after it has been built and validated against a known defect (`docs/validation.md`). A lead has not: it says "this entity is unusual here", not "this control failed". Folding leads into the score would move the validated ranking with signals nobody has validated, and about 40 metrics per entity means some will be extreme by chance. Kept apart, they widen what an examiner sees without weakening what the score means. On the synthetic dataset the scan raises no lead on any of the three entities with no injected defect (`tests/test_anomaly_scan.py`); that is evidence of restraint on clean synthetic data, not a false-positive rate on real submissions.
- **Consequences:** A lead an examiner confirms several times is a candidate for a new rule, written and validated like the others. The scan's thresholds are in `config/anomaly.yaml` and its hash is recorded in each run manifest.
- **Alternatives Considered:** Unsupervised ML (isolation forest, autoencoders): rejected by ADR-001 and harder to explain than "this rate is 4 robust standard deviations from the peer median". Scoring leads at a low weight: rejected for the reason above.

## ADR-008: Signed Audit Checkpoints (Ed25519), Tamper-Evident, not Tamper-Proof
- **Context:** ADR-005 leaves two attacks that the keyless chain cannot detect: removal of the newest entries and a full recomputation of the chain. Both are caught only by comparing against a checkpoint kept off-box. A checkpoint written down by hand has two weaknesses: it can be mistyped, and nothing proves who recorded it, so whoever controls the host could hand a verifier a "checkpoint" that matches a rewritten chain. (ADR-007 is reserved for a separate decision on another branch.)
- **Decision:** `satsa audit checkpoint --sign --key <private key>` emits a JSON checkpoint (format `satsa-audit-checkpoint/1`: chain, table, entry count, head hash, hash algorithm, UTC time, tool version) signed with **Ed25519** via the `cryptography` library. `satsa audit verify --checkpoint <file> --pubkey <public key>` checks the signature first, then that the live chain verifies and that its entry at the recorded position still has the recorded head hash: the chain must **match or extend** the checkpoint. `satsa audit keygen` writes the key pair with owner-only access (mode 0600 on POSIX; on Windows inheritance removed and Full Control granted to the current user only), and signing refuses a private key that other accounts can read. Implementation: `src/satsa/audit/` (`signing.py`, `keys.py`, `checkpoint.py`); tests: `tests/test_audit_tamper_matrix.py`.
- **Interface for post-quantum signatures:** signers and verifiers come from a registry keyed by algorithm name (`satsa.audit.signing.get_backend`). Only `ed25519` is implemented. `ml-dsa-44`, `ml-dsa-65` and `ml-dsa-87` are reserved names that raise "not implemented"; an ML-DSA backend can be added later as one registered class, without changing the checkpoint format or the CLI, and without a new dependency: the pinned `cryptography` 50.0.2 already provides ML-DSA-44/65/87 keys (`cryptography.hazmat.primitives.asymmetric.mldsa`, checked 2026-10-01). Any other name is rejected. ML-DSA was left unimplemented on purpose (the Phase 3 scope was Ed25519 only), and this does not change ADR-005's reasoning that integrity of the chain itself does not need post-quantum signatures; the interface only keeps that door open.
- **Verification stays in the CLI, not the web app:** a checkpoint is worth having because its verifier need not trust the supervisory host. A "verify checkpoint" page served by that same host could be made to say anything by whoever controls it, so checkpoints are verified with `satsa audit verify --checkpoint --pubkey` on the examiner's own machine (against a copy of the database). The web audit page verifies the chain alone and says so.
- **Possible hardening, not done:** encrypting the private key with a passphrase (`cryptography`'s `BestAvailableEncryption`). The key is protected by owner-only permissions and by being kept off the host; a passphrase would also protect it if the removable media were lost.
- **Key custody (the condition the guarantee rests on):** the private key must **not** live on the supervisory host. ADR-005's objection to signatures still holds for a key stored on the box: an insider with the database and the key can rewrite history and sign a matching checkpoint. Keep the private key on removable media held by the examiner (or sign on a separate machine from an exported head), and give the public key to whoever verifies. The checkpoint files themselves must also be kept off-box; a checkpoint the insider can delete protects nothing.
- **What it does and does not do:** tamper-**evident**, not tamper-proof. Nothing prevents deleting or editing rows; the checkpoint only makes such a change detectable later, and only for entries up to the last checkpoint. Entries written after the newest checkpoint are protected by the chain alone (ADR-004/005). Administrators and SYSTEM on Windows can read any file regardless of its ACL.
- **New dependency:** `cryptography` (with `cffi` and `pycparser`), justified because hand-written signature code is not acceptable for an audit control. It is a widely reviewed library, needs no network at run time, and publishes prebuilt `abi3` wheels for Windows and Linux (x86-64), so it installs from an offline wheelhouse (`uv.lock` pins `cryptography` 50.0.2).
- **Alternatives considered:** HMAC-signed checkpoints (the verifier would need the secret, so verifying would also let them forge); GPG (an external binary and keyring to manage on an air-gapped host); RSA (larger keys and signatures for no benefit here); an external timestamping authority (needs a network).

## ADR-009: Hypothesis for Property-Based Tests (Development Only)
- **Context:** the example tests check the cases someone thought of. Two classes of bug in this codebase were missed that way: evidence lists whose order depended on how rows happened to be stored (seven rules, one of which named the wrong analyst in its rationale), and ingest paths that could disagree on unusual input. Both are properties over all inputs ("the same rows in any order give the same finding", "the columnar and row paths store the same thing"), which a generator tests far better than hand-picked examples.
- **Decision:** add `hypothesis` as a **development** dependency (`[dependency-groups] dev` in `pyproject.toml`; pinned at 6.168.3 in `uv.lock`), used only by `tests/test_property_ingest.py` and `tests/test_property_rules.py`. Every test fixes its example budget (`max_examples`), so a run takes bounded time.
- **Not shipped:** it is not a runtime dependency. `scripts/build_wheelhouse.sh` exports with `--no-dev`, so it is in neither the offline wheelhouse nor the bundle, and nothing under `src/` imports it (`tests/test_dependencies.py` keeps cloud and telemetry packages out of `uv.lock` either way).
- **Offline availability:** it brings one dependency, `sortedcontainers` (pure Python). Hypothesis 6.168.3 publishes no pure-Python wheel; it publishes compiled `cp310-abi3` wheels (one per platform covers Python 3.10 and later) for Windows, Linux (manylinux x86-64 and aarch64) and macOS, plus an sdist, so a developer machine without network can install it from a wheelhouse built with `uv export --only-group dev` and `pip download --only-binary=:all:`. It makes no network calls; its example database is a local `.hypothesis/` directory, which is git-ignored.
- **Alternatives considered:** hand-written randomised loops (no shrinking to a minimal failing case, which is what made the ordering bugs readable); keeping only example tests (they had already missed the bugs above).

## ADR-010: Sanitise Every File, Never Guess What a Column Means
- **Context:** real CSE exports differ in encoding (Windows-1252 from Excel, UTF-16), separator, blank and ragged rows, header spelling and file format (Excel, enveloped JSON). Before this change a semicolon file read as one column, a Windows-1252 file or a type change after row 1,000 made the file unreadable, and `.xlsx` was not accepted.
- **Decision:** one source-agnostic layer, `satsa.ingest.sanitise`, reads every file into clean, unique headers and rectangular rows and records what it did. A clean canonical CSV keeps the previous Polars read (fast path); anything else is decoded, re-parsed with Python's `csv` module and handed to Polars as UTF-8 CSV, so types are inferred the same way on both paths. Rows are never dropped silently: blank rows are counted, cells beyond the header are counted and raised as the DQ warning `file_partly_read`.
- **What it deliberately does not do:** it does not map columns to canonical fields by guesswork, and does not resolve ambiguous dates (03/04/2026). A wrong mapping (e.g. "Last Updated" read as the closure time) would produce confident, wrong findings against a CSE, which is worse for a supervisory tool than a reported gap. Meaning comes from the canonical layout or a confirmed source mapping. Exact-duplicate rows are kept, since duplication is itself a DQ signal.
- **Excel without a dependency:** `.xlsx` is read with `zipfile` and `xml.etree` (first sheet, shared and inline strings, booleans, date styles, 1900/1904 epochs), so the offline wheelhouse is unchanged. Parts declaring a DOCTYPE are refused, and decompressed size is capped, against entity-expansion and zip-bomb inputs.
- **Alternatives considered:** `openpyxl` (a new runtime dependency to vendor into the air-gapped bundle, for a feature the standard library covers); `charset-normalizer`/`chardet` for encoding detection (byte-order marks, then strict UTF-8, then Windows-1252, then Latin-1 is deterministic and covers the exports seen so far, including a Cortex XSIAM case export saved as Windows-1252; Latin-1 maps every byte, so decoding cannot fail).

## ADR-011: Account for Every Row; Keep Row References, Not Rejected Rows
- **Context:** rows a source mapping could not fill (an empty required field, a timestamp it could not parse) were dropped with no count, no DQ issue and nothing in the ingest result, so a supervisor could not tell that an assessment rested on part of a submission. Separately, a canonical file that neither its name nor its headers identified was stored as alerts by default.
- **Decision:** a per-file ledger (`satsa.ingest.ledger`) records rows read, rows stored per table, rows a mapping leaves out of a table on purpose, and rows rejected, grouped by reason with the row as the file numbers it (spreadsheet row, JSON record, NDJSON line; the sanitiser keeps the positions of the blank rows it dropped so the numbers still match the file). Rejections a mapping causes are raised as the DQ issue `rows_rejected`: an error when half a file or more is lost, otherwise a warning. A file that nothing identifies is reported as `file_not_recognised` and not stored.
- **A row is lost only if no table took it:** one export can feed several tables (TheHive's alert export feeds `alert` with every alert and `case_alert_link` with the alerts that have a case). An alert with no case is stored as an alert, so it is reported as "not for `case_alert_link`", not as a rejection. A row no table took is reported once, under the first table the mapping lists.
- **Why no quarantine store of rejected rows:** a rejected row's other cells can hold names, free-text comments or addresses, which SAT-SA only ever stores pseudonymised or redacted. Keeping raw rejected rows would bypass that. The row number lets the entity find and correct the row in its own export.
- **Alternatives considered:** a quarantine table holding the raw rejected rows (rejected for the privacy reason above); keeping the default-to-alert behaviour (rejected because rows of an unknown kind would count as alerts and rules would read their columns); a row-number column added to every frame (rejected because it would flow into canonical tables and change the stored data; positions are mapped back through the sanitiser's report instead).

## ADR-012: Cortex XSIAM Case Export, Recognised by Its Columns, Mapped to Cases Only
- **Context:** the first real CSE export received is a Cortex XSIAM case list: one case, 57 columns, Windows-1252, ordinal dates, saved under an arbitrary file name. The upload page read it in the canonical layout, where only some columns matched and its 1,266 timer-only rows would have been stored as cases.
- **Decision:** `config/mappings/cse_cortex_xsiam.yaml` maps the case list to the `case` table (id, severity, status, pseudonymised owner, opened and resolved times). A mapping table may list `headers:`, the columns that identify its export; `detect_source_mapping` picks a mapping when one of its tables' headers is present and it describes every submitted file, so the CLI (without `--source`) and the upload page translate the export whatever it is called. Identifiers from a mapping are stored as text.
- **Resolution reason and comment are not mapped to closures:** the closure table belongs to alerts (EG02 and EG04 join it to alert ids). Case-keyed closures would never be read, yet would mark those rules as assessed: a coverage claim the data does not support. They are listed as unused columns.
- **Time zone:** the export does not record its zone. `+05:30` is assumed in the mapping, as for ServiceNow, and stated in the file and in `docs/connectors.md`; it is the first thing to check against a CSE's console settings.
- **Limits:** built and tested against one real case plus a synthetic export of the same shape; statuses other than Resolved are taken from the product's documented values and marked "not seen". The case list alone supports one rule (EG09); alert-based rules need the XSIAM Issues export. Detection matches declared column names exactly and never chooses between two qualifying mappings.
- **Alternatives considered:** matching the export by file name (XSIAM names exports arbitrarily); fuzzy column matching to the canonical layout (a guess, see ADR-010); deriving workflow events from the creation and resolution times (they would repeat `opened_at`/`closed_at` as if they were an audit trail).
